  When you run JavaScript in the browser, it doesn't just run "pure JavaScript" — it runs JavaScript + Web APIs provided by the browser (Chrome, Firefox, etc.). These are not part of core JavaScript, but the browser provides them via the DOM API.

- Difference between caret(^) & Tilde(~) in dependency version: Caret(^): Allows updates that do not change the leftmost non-zero digit. Meaning: Accept minor and patch updates, but not major. - Significance of package-lock.json: The package-lock.json file is critical for ensuring consistency and reliability in Node.js projects. Exact Dependency Versions: While package.json specifies version ranges (like ^1.2.3 or ~4.5.6), package-lock.json locks down the exact versions of every package (and its sub-dependencies). It Ensures that everyone on your team, as well as your production builds, uses the same versions of dependencies. Faster Installs: It contains a full dependency tree with resolved versions and URLs, so: npm doesn’t need to re-resolve all versions. Installations are faster and deterministic. Reproducible Builds: You get the exact same environment every time, even on different machines or CI/CD systems. No surprises like: “It works on my machine but not in production.” Dependency Tree Tracking: It tracks: Nested dependencies (what each package depends on), Resolved URLs, Integrity hashes (to validate integrity of installed packages). Helps with Audits and Security: Tools like npm audit use package-lock.json to: Check actual installed versions, Identify known vulnerabilities, Suggest appropriate upgrades. Always commit it for: Apps, Projects with reproducible builds.

- Transitive Dependencies: Transitive dependencies are dependencies of your dependencies — packages that your direct dependencies rely on, but that you didn’t explicitly install. Bugs, vulnerabilities, or version conflicts in transitive dependencies can affect your app, even if your direct dependencies are fine. Tools like npm audit scan transitive dependencies for known vulnerabilities.

- **HMR(Hot Module Replacement)**: Automatically refreshing our page after saving the changes by reading all the files for changes. It is a feature provided by modern bundlers like Webpack, Vite, Parcel, etc., that allows you to: Update modules in a running application without a full page reload. Although it is used only for development purpose not used in production builds. HMR is designed to improve the developer experience — for fast feedback and preserving app state during changes.

**HMR is useful in many ways**:

- Faster Development: Only the changed code is reloaded — not the entire page.
- Preserves State: Unlike a full reload, your app state (e.g., form inputs, Redux store, component state) stays intact.
- Improved Productivity: You see changes instantly, which makes debugging and UI tweaking much smoother.
  **Workflow of HMR (Simplified Flow)**:
- You save a file (e.g., App.js)
- The bundler detects the change
- It recompiles just that module
- The browser receives the updated module
- That specific module is replaced in the app, without reloading the page
  **Why HMR is not used in production**:
- Performance Cost: HMR adds extra logic, metadata, and WebSocket connections to track module changes — which are unnecessary and inefficient in production.
- Production Builds Are Static: Production builds are optimized, bundled once, and typically served as static files from a CDN or server. These files don’t change after deployment.
- Security & Stability: Automatically swapping code at runtime in production could introduce instability, bugs, or vulnerabilities.

- Production build takes more time than dev builds because production builds are highly optimized, minified, compressed and hence is higly performant.

- **Props**: Props (short for properties) are read-only data (object type) that you pass from a parent component to a child component. They are function arguments for your component because component at the end of the day is JS functions in functional components. So, passing "props" to a component is just like passing arguments to a function. **Props solves a fundamental UI need**: data reusability and flexibility. Without props: You’d hardcode values inside components (making them rigid), you’d need multiple versions of the same component for different data. **With props**: Components become reusable & dynamic. The same button, card, or table component can handle different text, styles, or behavior just by changing props. **Problems props solves are**: Avoids duplication — one component can serve multiple purposes, Keeps UI consistent — same base component with different data. Makes code maintainable — changes in one component propagate everywhere it’s used. Improves scalability — big apps need flexible components. **Limitations of Props**: Props are one-way: Parent → Child only. A child cannot directly update a parent’s state via props (because props are read-only). In deeply nested components, passing props down multiple layers becomes prop drilling (messy and hard to maintain). **Better Alternatives**: When props become messy (especially with prop drilling), you can use - Context API: Shares data globally without passing props manually at every level. Good for theme, authentication state, language settings, etc. | State Management Libraries (Redux, Zustand, Jotai, Recoil): Best when your app has a lot of shared data across unrelated components. Adds features like middleware, async state, and debugging tools. | Event Callbacks (Child → Parent Communication): Instead of updating props, a child can call a function passed from the parent to request changes. Hence props are perfect for local, simple data passing from parent → child but avoid for large-scale state sharing across multiple deep components — use Context or state libraries instead and also Keep props minimal — too many props make components hard to use.

- Why should we give **"key"** attribute/property to each element while rendering a list, why it is necessary or helpful, what problem it solves and what if we dont use this "key" property/attribute?

---

In React, when you render a list of elements using .map() (or similar), you must give each element a special prop called "key". This "key" helps React identify which items in the list have changed, been added, or removed between renders. React uses a process called Reconciliation: When state/props change, React re-renders the component, instead of re-rendering the entire DOM, React compares the virtual DOM (old vs. new), and if an item’s key is the same between renders, React reuses that DOM element instead of recreating it but without keys React guesses based on index/position in the array, which can cause unnecessary re-renders or bugs (especially if the order changes). Using "key" helps in performance boost due to fewer DOM updates and prevents bugs because component state inside list items stays with the correct element. Without unique keys, React’s diffing algorithm can misinterpret changes which can lead to wrong UI updates. And we should not use "Index" as key because using index as keys is safe to use only when list is static (never reordered, filtered, or modified) and also no local state is stored inside list items otherwise inserting/removing items can shift indexes which can lead to keys change and then React destroys and recreates DOM nodes which can also cause flickers or loss of state hence we should use a unique, stable identifier (like id from the database).

- **Virtual DOM**: For every UI, React creates a Virtual DOM (JavaScript Object), Virtual DOM is not an actual DOM because Actual DOM are made up of tags like: <div>, <h1>, <span> etc., while Virtual DOM is a representation of an Actual DOM and with representation means the object(JS Object) or the React Element/Component and a React Element or Component is under the hood a plain JavaScript Object because React creates an object of every React Component. So, the final Virtual DOM tree is basically a nested JavaScript Object representation of an Actual DOM. Virtual DOM is a JavaScript Object representation of DOM and it is not just associated to React only this concept is present from long back, React just used it in its own algorithm.

- **Diffing Algorithm**: React tracks or constantly monitors the state variable of a component(created using useState hooks) if present and whenever there is a change in the state variable of any React Component, React re-renders that component and update the UI with the updated value/data which creates two Virtual DOM and then with the help of Diffing Algorithm React finds out the difference between two Virtual DOM's which are basically the Old Virtual DOM and the New Virtual DOM and then paints the delta/difference to the Actual DOM on every render cycle. And since we know that Virtual DOM is JavaScript Object(React Element are JS Object under the hood) hence calculating difference between two JavaScript Object is fast in comparison to two HTML(Actual DOM).

- **Reconciliation**: Reconciliation is the process React uses to update the DOM when the state or props of a component change. React maintains a Virtual DOM (a lightweight copy of the real DOM). When something changes (like state/props), React creates a new Virtual DOM tree, compares (diffs) it with the previous Virtual DOM, finds the minimal set of changes and finally updates the real DOM efficiently, this whole process is called Reconciliation. The real DOM is slow to update, if React re-rendered everything from scratch then performance would drop hence instead React figures out what actually changed and updates only those parts. This makes React app faster, less memory use, and gives smooth UI experience. How Does Reconciliation Work: Element Type Rule: If the type of element is the same, React reuses the existing DOM node and updates its attributes. If the type changes, React destroys the old node and builds a new one. | Children List Rule: When rendering a list, React compares items by their keys. With keys → If React sees items are just reordered then it reuses them. Without keys → React thinks both are new → destroys old nodes & creates new ones → bad for performance. | Component Rule: If the same component is rendered with new props, React reuses the component instance and just updates props. If component type changes → React unmounts old component and mounts a new one.

- Reconciliation is React’s diffing algorithm that makes UI updates fast by reusing as much of the existing DOM as possible instead of re-rendering everything.

So the answer to this is: in react we change/modify the state varibale through setter function provided by useState hook, and whenever the change or basically setter function of a state variable is triggered, react re-renders that whole component by calling the component function once again and react updates the dom with the updated value of that state variable and this time this state varibale which has changed is not the same variable or same instance of that variable which was earlier with previous value instead it is a new instance or new variable with same name as previous but with the updated/changed value (passed through setter function). And remember calling the component function is equivalent to rendering/re-rendering that component.

- While re-rendering the component during reconciliation process react with the help of diffing algorithm updates only the changed/updated/modified part within the component despite re-render of the whole component which is why react is considered fast in dom manipulation. You can try using console.log and you'll notice that whole component code (function body) is getting called again but on UI only the specefic part or section is updated.

- **React Hooks**: **useEffect** - useEffect is provided by react library and it lets you run side effects in functional components. A side effect is anything outside the scope of rendering UI like: Fetching data, Subscribing to events, Changing the DOM manually, Setting up timers, Logging etc. Class components uses componentDidMount, componentDidUpdate, componentWillUnmount and useEffect replaces all of these in functional components. useEffect hook is called using useEffect function which takes a mandatory callback function as its first argument and a dependency array as its second argument which is optional. Now, although the basic nature of useEffect is to be called on each component render but dependency array which is second argument of useEffect hook decides when and how many times the useEffect will be called within the component hence dependency array changes the behaviour of the useEffect call. When we don't put dependency array, useEffect is called everytime when the component renders or re-renders. When we have empty dependency array, then useEffect will be called only once for initial or first render when app loads for the first time. And lastly when we use non-empty dependency array which means our dependency array has one or multiple dependency state variable then the useEffect will be called once during initial or first render of the component and then it will be called after every change/update in any of the dependency from dependency array. So the common among all three cases is that the useEffect hook will always be called on first or initial render of the component.

- **Best practices while using lifecycle hooks**: Never use or declare state variables (useState) outside of your component body as it makes no sense because it wont work instead it will throw an error: "Invalid hook call, Hooks can only be called inside the body of the functional component". Hence always call useState(local state variables) inside your body. UseState hook has a specefic purpose and that is to create local state variables inside your functional component. And also try to call the hooks at the top of the component where function starts to avoid inconsistency as we know javascript is a synchronous single threaded language where code will run line by line hence the best practice is to to first define the state variables at top and it also helps react to understand the code properly and prevents inconsistency in the code. Also never use useState hook or create your state variable inside if else block, inside for loop, inside functions or infact inside any condition.

- **Linking html content with routes/pages**: Traditional way of linking html content with routes/pages using anchor tag and giving route/path in **href** attribute is not considered a best practice when using react and should be avoided because routing through links using anchor tag refreshes the whole page, while it can be avoided means we can navigate to other routes/pages using links but without refreshing our whole page. So **react-router-dom** provides us a super powerful component called **Link** which is used similarly like an anchor tag but prevents our page from getting refresh and prevents our app getting slow. The only difference between an anchor tag and Link component is the different attribute name for providing route/path. In anchor tag we use attribute named **href** to pass route/path while in Link component we use attribute named **to** to pass route/path. Link component refreshes the component while navigating but anchor tag reloads the whole page. And this functionality contributes to **Single Page Application**. Although if you will see in browsers html, you will notice that there is no link component or tag instead it will show anchor tag only, this is because react uses anchor tag under the hood, and link tag/component is kind of wrapper over anchor tag, but in react code we use link because this link tag helps react-router-dom to keep track of the link content and does not refreshes the whole page.

- **Single Page Application**: A whole single page/component like App or AppLayout where all other child components/pages like Header, Navbar, Body, Footer etc interchange themselves according to navigation, everything is a component in react, even when we shift to new route that is also another component which is why we call it a single page application. Traditionally we used to have a different html pages like index.html, about.html, contact.html etc and we used to navigate among these pages via anchor tag where each pages used to rendered from server but with react we do not reload our app or refetches the page when we navigate through links also our browser will not make an external call to load different pages.

- **Routing**: means deciding what content to show when a user visits a particular URL. Routing answers the question: Which page/component should be displayed for this path? There are two types of routing in our web applications: Client Side Routing and Server Side Routing. Before React or SPAs existed, routing was handled entirely on the server. **Server Side Routing**: Lets say we have about.html and contact.html page in our web app and when we click on link/tab for "/about" it reloads the whole page send the network call to about.html and fetches the html and renders it on to the browser/UI, so this is called server side routing. So we make a network call and the requested page is coming from server. **Client Side Routing**: We do not make any network call for any page or component because all the components/pages are already loaded into our app. When we load the app for the first time it already had the code for all component/pages like about, contact etc, so when we navigate to about or contact page it just loads that components hence in client side routing we do not fetch the page.

- **Server Side Routing**: Before React or SPAs existed, routing was handled entirely on the server. **How it worked**: User enters example.com/contact --> Browser sends a HTTP request to the server --> Server looks at the path "/contact" --> Server loads/creates an HTML page --> Browser receives the full HTML file and renders it. **Characteristics of Server-Side Routing**: full page reload every time, very good SEO as server returns full HTML, slower routing speed due to round trips to server, simple for small sites, all rendering done on the server.

- **Client-Side Routing** (Used in React, Vue, Angular): Modern apps use JavaScript to handle routing inside the browser itself. **Working**: User enters /products --> Browser loads index.html once --> JavaScript router (like React Router) reads the URL --> Router dynamically shows the matching component without reloading the page. No additional full-page HTTP requests. Only API calls happen in background (AJAX / fetch). **Characteristics of Client-Side Routing**: no page reload — instant navigation, weak SEO unless SSR/Hydration used, is super fast after initial load, advanced complexity, requires JS router, rendering happens in browser.

- **Why Client-Side Routing Became Popular?** : Because it enables Single Page Applications (SPAs). In an SPA: Only the first request loads HTML, CSS, JS, After that, everything happens inside the browser, Navigation feels like mobile apps: smooth + instant.

- **Why Not Use Only Server-Side Routing?** : Issues with traditional server routing: Slow page switches (full reload), More network usage, UI feels “heavy”, Hard to create dynamic, interactive apps (Dashboards, Gmail, YouTube).

- **React + Client-Side Routing = SPA** : React uses: React Router to control components based on URL, History API under the hood (pushState, replaceState), No reload needed — DOM updates like a normal component tree change. Example: /dashboard → Render <Dashboard/>, /profile → Render <Profile/>.

- **Is Client-Side Routing enough?** : Not always — for SEO-heavy websites (blogs, eCommerce) you need: **SSR (Server-Side Rendering)** where framework renders HTML first on server (used in Next.js) | **Hydration** React attaches event listeners after HTML is loaded | Hybrid Routing = SSR + CSR --> Most modern frameworks support this.

- **Client-Side Routing Problems & Solutions** : Problem 1 — Bad SEO - Solution: Next.js (SSR) | Problem 2 — Large initial bundle - Solution: Code splitting + Lazy loading routes | Problem 3 — Slow first load - Solution: Streaming SSR + hydration.

- **Dynamic Routing**: Instead of having hard coded routes we switch to dynamic routes where part of URL is variable means it changes according to the data or pages we have to load. It means this variable part of he URL decides what data or page to show. How do we define dynamic routes/path in react-router --> **/user/:id** here "id" is the dynamic part of the URL. Why do we need dynamic routing ? --> Real-world applications deal with dynamic data, not fixed pages and creating a route for each item manually is impossible and is not good practice. Dynamic routing solves this problem by: Using one route, Handling many URLs and Rendering the same component with different data. Now in case of dynamc routes/path we need to read the variable part of URL, it could be name, id, or any unique identifier, so in order to fetch the dynamic data for each content which is generally fetched from API in a standard enterprise application, we need to read the id from the URL and for that we use **useParams** hook provided to us by **react-router-dom** which fetches the dynamic part of URL, so we can just extract our defined param from useParams hook like --> const {resId} = useParams(); and now we can use this param while making an API call and load the dynamic data within same single component because generally the content id changes within the URL and rest remains the same. And finally we can use **link** tag provided by **react-router-dom** and define the path for each content within **to** attribute of link tag by combining constant + dynamic part (id).

- **Class Components**: Just like a react functional component is a normal javascript function that returns some piece of JSX, similarly a class component in react is a normal javascript class that extends **React.Component** and has a **render** method in it that returns some piece of JSX. **React.Component** is also a class that is given by react to which our custom class based component extends. This React.Component comes from "react". We can export in the same way we export our other functional based components and also importing and using it is same as we do with functional components. There's a difference in the way we recieve **props in class based components**, in functional components we directly recieve props in the function's arguments and destructure it there only if needed, but in class components we recieve props in class constructor arguments and we also need to make call to super (parent class contructor calling) along with the recieved props.

- Now the question arises --> **Why do we have to call super along with props ?**: First of all if we are about to use **this** keyword within our constructor or class component, we need to call **super()** with the class constructor as it is language rule nothing related to react, calling "super()" calls the parent or base class constructor which initialzes "this" and if we dont call "super()" and try to use "this.props" within the child/derived class constructor, it will throw undefined error.

- Now second part of this question would be --> **Why do we need to send "props" along with "super()" calling ?**: **React.Component** internally stores "props" like this: **this.props = props** but this assignment happens inside the parent constructor (React.Component). So, if you are using a constructor and accessing "this.props" you need to make a call to **super(props)** at the beginning of your constructor method. But if we don't define constructor method then there is no need of "super(props)" and if we are recieving props but not using props inside our constructor method then we can call like this --> "super()" although technically alowed but it is not considered a good practice.

- Loading/Mounting a function based component means **invoking** that functional component while loading/mounting a class based component means creating an **instance** of that class component. And whenever an instance of class is created it's constructor is called and it is the **best place to receive the props and create state variables**. State variables and Props are all bind to "this" keyword in class component. So you can define this.state as an object within the constructor of the class component and keep all the state variables within that object which you need to use throughout that class component.

- Earlier before functional component and hooks introduction this is how we used to create the component in react and use state variables and props within the class component.

- **Updating state variables in class based components**: Never ever update your state variables directly in class based compnents like --> this.state.count = this.state.count + 1; this is wrong, it won't work and instead it will create inconsistency. In class based component we update the state variables through **this.setState({count: this.state.count + 1})** method and we pass the state variable object which we want to update as an argument to this method. And whenever the state variable is getting updated react re-renders the component with the updated value. If on a certain operation we want to update multiple state variables then we need not call setState separately for each state variable instead we can batch all within one setState and update them together and react will only update those state variables which are passed in setState({...}) without touching other state variables. React does this by finding the diff and then it will enables the reconciliation process and update the dom.

- **Lifecycle methods of class based components and their order**: In a class based component, if we talk about its lifecycle methods among **constructor**, **render** and **componentDidMount** method then their order of being executed are: **constructor() --> render() --> componentDidMount()**. Whenever a class based component is loaded/mounted on browser it is basically an instance created of that class (instantiation) and hence their constructor method gets called first, then after that its render method gets called and post complete render finally its componentDidMount method gets executed.

- **Order of lifecycle method of class component in parent-child relation**: Lets say there is a parent class component and it import and uses a child component within its skeleton/body in render method, so in that case the order of execution of lifecycle methods of parent-child are: **Parent Constructor --> Parent Render --> Child Constructor --> Child Render --> Child componentDidMount --> Parent componentDidMount**

- **componentDidMount Method**: componentDidMount lifecycle method of class based component (similar to useEffect hook used in functional component) used to fetch data through API calls once the component mounted on browser UI. As the name suggest it gets executed after component is mounted/loaded on browser because we do not want to block the rendering while API call because API call can take time, hence its better and fast approach to load/mount the component first and then fetch the data by making an API call and update the component with the latest data and re-renders the component.
